# Side channels: where masking happens decides whether they exist

Generated by `python -m attacks.side_channel_analysis`. Every number below is measured, not asserted.

## The setup

`mr-agent-1` holds a delegated credential for grant `g-main`, narrowed to EU with **no cost columns**. It legitimately sees 5 rows, and `unit_cost_usd`/`margin_pct` must be hidden in all of them. The true hidden values are:

| shipment_id | unit_cost_usd | margin_pct |
|---|---|---|
| 1003 | 11.00 | 22.50 |
| 1002 | 6.25 | 18.00 |
| 1001 | 4.50 | 12.50 |
| 1006 | 3.75 | 14.00 |
| 1005 | 2.10 | 8.00 |

True cost ordering (descending): `[1003, 1002, 1001, 1006, 1005]`. True sum: `27.60`. True max margin: `22.50`.

## The finding

Both arms mask the columns in what they return: the caller sees NULL for `unit_cost_usd` in every row, in both arms. Both arms also pass all five positive controls, so neither is winning by being stricter. The difference is **when** the masking happens relative to the caller's own SQL.

* **RLS arm** — masking is a `CASE` in the target list of `portal.shared_shipment`. The caller's `WHERE`, `ORDER BY` and aggregates are applied to a relation in which the value is *already* NULL.
* **appfilter arm** — the query runs against the real column in the database, and Python nulls the field out afterwards. Every SQL construct the caller supplies still sees the true value.

### 1. Predicate over a masked column

`WHERE unit_cost_usd > N`, same credential, same rows:

| N | RLS arm returns | appfilter arm returns |
|---|---|---|
| 0 | `[]` | `[1001, 1002, 1003, 1005, 1006]` |
| 3 | `[]` | `[1001, 1002, 1003, 1006]` |
| 5 | `[]` | `[1002, 1003]` |
| 10 | `[]` | `[1003]` |
| 100 | `[]` | `[]` |

The RLS arm returns the same result (1 distinct result set across all thresholds) because `NULL > N` is never true — the predicate cannot distinguish rows and so discloses nothing. The appfilter arm produces 5 distinct result sets, which is a working comparison oracle: each additional threshold narrows a hidden value, so a partner recovers all five costs in a handful of requests. **Every one of those requests is a legitimate, fully-authorized query.**

### 2. ORDER BY a masked column

| arm | `ORDER BY unit_cost_usd DESC` | `... ASC` | leaks ranking |
|---|---|---|---|
| RLS | `[1001, 1002, 1003, 1005, 1006]` | `[1001, 1002, 1003, 1005, 1006]` | **no** |
| appfilter | `[1003, 1002, 1001, 1006, 1005]` | `[1005, 1006, 1001, 1002, 1003]` | **yes** |

The appfilter arm's descending order is `[1003, 1002, 1001, 1006, 1005]`, which is the true cost ranking `[1003, 1002, 1001, 1006, 1005]` restricted to the agent's visible rows. The values are NULL and the *ordering still hands over their relative magnitudes*. The RLS arm's two orders are identical, so the sort key carried no information.

### 3. Aggregates over a masked column

| aggregate | RLS arm | appfilter arm | true value |
|---|---|---|---|
| `sum(unit_cost_usd)` | `[0]` | `[28]` | 27.60 |
| `max(margin_pct)` | `[0]` | `[23]` | 22.50 |
| `count(*)` | `[5]` | `[5]` | 5 visible |

The appfilter arm's aggregates are computed before masking, so they return the true totals of data the grant explicitly withholds. Note `count(*)` is correct in **both** arms: it does not touch a masked column, and both arms restrict rows correctly. Only the column-level limits differ, which is why the row-level and column-level claims have to be tested separately.

## Why this is the argument for database-enforced masking

The appfilter arm is not a strawman. It implements every rule the policy implements — region scope, classification ceiling, partner restriction, column masking, grant liveness, delegation-chain expiry — in clear Python, and it passes all five positive controls plus 26 of 30 attacks. It fails only where the caller's own SQL touches a column it was going to mask afterwards.

That is the general lesson: **application-level masking is only as strong as your enumeration of the ways a query can observe a value.** Filtering the result set is not the same guarantee as never letting the value into the query. Projection-time masking inside the view is strictly stronger because it removes the value before any caller-supplied expression can reference it.

## What is still open

* **Base-table cardinality** leaks through `pg_class.reltuples` to any role that can read the catalog, including one with no privilege on the table (see `attacks/metadata_cardinality.py`). RLS protects contents, not relation size. Mitigated operationally — partners call the read API and never receive a database connection — not cryptographically.
* **Timing** is not measured. Response time varies with the number of rows scanned, so a determined partner could infer cardinality that way.
* The RLS arm's immunity here is a property of masking in the view's target list. A future column added to the view *without* its `CASE` guard would reopen all three channels, which is why `tests/test_view_masking.py` asserts every sensitive column is guarded rather than trusting review.
